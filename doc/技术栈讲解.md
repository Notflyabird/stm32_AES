## 一、项目背景与定位

⏱ 3 min

### 讲解词

> 大家今天要了解的这个项目，是一个运行在 **STM32F103** 上的 **Flash Bootloader**，简称 **FBL**。
>
> 那 Bootloader 是干什么用的？简单说，它是芯片上电后第一个运行的程序，它的职责是——决定"我是直接启动现有的应用程序，还是等待外部命令来更新它"。
>
> 我们这个 Bootloader 最核心的特点在于：**它通过 CAN 总线来实现远程固件升级**。通信协议用的是汽车行业的标准协议——**UDS（统一诊断服务）**，底层传输走的是 **ISO-TP（ISO 15765-2）**。
>
> 说白了，这就是一套 **"给汽车 ECU 做 OTA 升级"** 的完整方案，只不过我们的目标芯片是 STM32F103 这颗通用 MCU。
>
> 项目的亮点有几个：
> - 支持 **16 个 UDS 诊断服务**，覆盖了从会话控制、安全访问到数据传输的完整流程
> - 使用 **AES-CMAC** 做安全认证，防止非法刷写
> - 具备 **独立看门狗 IWDG**，确保程序跑飞了能自动复位
> - 而且整套代码跑在 **只有 64KB RAM、512KB Flash** 的 Cortex-M3 上，资源很紧张，所以每一行代码都要精打细算

### 要点提炼

| 项目 | 内容 |
|------|------|
| 芯片 | STM32F103ZET6 (Cortex-M3, 72MHz → 64MHz) |
| 存储 | Flash 512KB + SRAM 64KB |
| 上行协议 | UDS (ISO 14229-1) over CAN |
| 传输层 | ISO 15765-2 (ISO-TP) |
| 安全认证 | AES-128 CMAC (RFC 4493) |
| 看门狗 | 独立 IWDG，500ms 超时 |
| 核心能力 | CAN 总线远程固件刷写 (OTA-like) |

## 二、硬件平台选型

⏱ 3 min

### 讲解词

> 主芯片我们选的是 **STM32F103ZET6**，这是意法半导体 STM32F1 系列的顶配型号。
>
> 为什么选这颗？几个原因：
>
> 第一，**成本敏感**。F1 系列是市场上最成熟、最便宜的 ARM Cortex-M3 MCU 之一，一颗 ZET6 在工业量级采购价也就几十块钱。
>
> 第二，**资源够用**。512KB Flash + 64KB RAM 对 Bootloader 来说绰绰有余。我们 FBL 只占 32KB，剩下 80KB 留给 APP，还留了 8KB 隔离区。
>
> 第三，**外设齐全**。芯片自带 CAN 控制器，我们只需要外加一个 CAN 收发器就能接总线。而且 STM32F1 的 HAL 库生态非常成熟，开发资料多，踩坑成本低。
>
> 外设的具体配置如下：

### 外设速览

| 外设 | 引脚 | 配置 | 用途 |
|------|------|------|------|
| **CAN1** | PA11(RX) / PA12(TX) | 500kbps, 中断接收 | UDS 诊断通信 |
| **USART1** | PA9(TX) / PA10(RX) | 异步, DMA TX | 调试日志输出 |
| **IWDG** | 内部 LSI 振荡器 | 预分频 8, 重装载 2500 | 系统防死锁 |
| **GPIO** | PC0 | 推挽输出 | LED1 状态指示 |
| **SWD** | PA13 / PA14 | 调试接口 | 程序下载与调试 |

> 这里特别说一下 **IWDG 看门狗**。它的时钟来源是芯片内部独立的 40kHz LSI 振荡器，不依赖系统主时钟，所以即使主时钟挂了，看门狗仍然在工作。
>
> 我们的配置：40kHz → 预分频 8 → 5kHz（200µs/tick）→ 重装载 2500 → 总超时 **500ms**。
>
> 在主循环里我们每 **~250ms** 刷新一次，留了一半余量。这样即使程序卡在主循环的某个地方，最多 500ms 后就会自动复位。

> 硬件平台看完了，接下来我们看看——芯片上电之后，Bootloader 是怎么决定"我是升级还是启动APP"的。

## 三、系统启动流程

⏱ 5 min

### 讲解词

> 这是一张启动流程图，我带着大家走一遍。
>
> 芯片上电复位后，先从 **SystemInit()** 开始——配置系统时钟。我们用的是 HSI 内部振荡器，经过 PLL 倍频到 64MHz。为什么不超频到 72MHz？因为我们对时序没有极端要求，64MHz 能有效降低功耗和 EMI。
>
> 时钟初始化完，就是 HAL 库和外设的初始化：CAN、USART、GPIO、IWDG、DMA 逐个启动。
>
> **接下来是关键——三阶段判决逻辑：**

```
第一阶段: RAM 回退标志
  检查 0x20000FFC == 0xABCD1234 ?
  ├─ 是 → 这是 APP 要求回退到 Bootloader → 进入 FBL 主循环
  └─ 否 → 进入第二阶段

第二阶段: Flash APP 有效标志
  检查 0x0800A000 == 0x5A5A5A5A ?
  ├─ 是 → APP 存在 → 进入第三阶段
  └─ 否 → APP 区域无效 → 直接进入 FBL 主循环

第三阶段: CAN 请求检测
  延时等待 CAN 总线上的会话请求 (10 02)
  ├─ 收到 → 停留在 FBL，处理 UDS 指令
  └─ 超时 → boot_jump() 跳转到 APP
```

> 这个设计考虑了两个场景：
>
> 场景一：**首次烧录**。Flash 里没有 APP，有效标志不存在，所以直接进入 FBL，等待主机通过 CAN 下载固件。
>
> 场景二：**正常启动**。APP 已经存在。如果 APP 想升级，它可以在自己的代码里设置 RAM 标志然后复位——这样 Bootloader 就不会跳转回 APP，而是等待新的固件。
>
> 如果没有任何干预，默认行为就是延时等待一会儿 CAN 请求，没收到就直接跳 APP，保证正常功能不受影响。
>
> 跳转函数 `boot_jump()` 干的事情很简单但很关键：关全局中断、关 SysTick、把 MSP 指针指向 APP 向量表的起始地址，然后跳过去。这一步要干净利落，不留任何中断残留。

### 要点提炼

```
上电 → 时钟初始化 → HAL 初始化 → 三阶段判决 → FBL 或 APP

判决优先级: RAM 标志 > Flash 有效标志 > CAN 超时等待
```

## 四、软件架构分层

⏱ 7 min

### 讲解词

> 整个 FBL 的软件架构分成 **四层**，从下往上分别是：

```
┌──────────────────────────────────────────────┐
│  UDSLogic 层: 16 个 UDS 服务实现，每个 SID 独立文件 │  ← 业务逻辑
├──────────────────────────────────────────────┤
│  UDSBase 层: ISO-TP 传输 + 服务分发 + 会话管理  │  ← 协议核心
├──────────────────────────────────────────────┤
│  Core 层: CAN / USART / Flash / GPIO 驱动     │  ← 硬件抽象
├──────────────────────────────────────────────┤
│  RingBuf 层: CAN 消息环形缓冲队列              │  ← 数据搬运
└──────────────────────────────────────────────┘
```

> 我们从下往上来讲。

### 第四层 — RingBuf 环形缓冲

> 最底层是一个 **环形缓冲区**，代码来自孔佳伟的开源实现。它用 C 宏实现了一个通用循环队列，head、tail、length 三个字段管理读写。
>
> 上层封装了 `msg_buf`，专门用来缓冲 CAN 接收到的消息。CAN 中断里把收到的帧塞进去，主循环里再取出来处理——**生产者和消费者模式**，避免中断处理耗时太长。

### 第三层 — Core 硬件抽象

> Core 层是 HAL 库生成的代码加上我们自己写的驱动封装：
>
> - **can.c** — CAN 初始化配成 500kbps，中断接收。收到帧后回调到 UDS 的端口层。
> - **flash_erase.c / flash_program.c** — 对 HAL Flash 操作做了封装。这里有个细节：STM32F1 的 Flash 写入必须按 **半字（16-bit）** 操作，不能逐字节写，我们在驱动里处理了这个限制。
> - **boot_jump.c** — 刚才讲启动流程时提到的跳转函数。
> - **aes_cmac.c** — 纯软实现的 AES-128 CMAC 认证算法。没有用硬件加密引擎，因为 F1 系列不带，所以全部用查表和异或实现。

### 第二层 — UDSBase 协议核心

> 这一层是项目最核心的部分，属于 **移植的通用 UDS 协议栈框架**：
>
> **uds_port.c** 是端口适配层，像胶水一样把具体 MCU 的 CAN 驱动和协议栈粘在一起。你需要实现的就是初始化函数、1ms 定时器任务、CAN 帧发送和接收回调。
>
> **uds_tp.c** 实现了 ISO-TP 传输层。这一层有大约 36KB 代码，是整个项目中最复杂的模块。它负责把超过 8 字节的 UDS 报文拆分成多帧，处理 SF、FF、CF、FC 四种帧类型的交互，还有 STmin、Block Size 这些流量控制参数。
>
> **uds_service.c** 是服务分发器，收到一个 UDS 请求后，它根据 SID 查找服务表，检查当前会话是否允许、安全等级是否满足，然后分发给对应的处理函数。S3Server 定时器（5s 超时）也在这层管理。

### 第一层 — UDSLogic 服务实现

> 最上层是 **具体的 UDS 服务实现**，每个服务都单独一个文件，互不干扰。目前支持 16 个 SID。
>
> **service_cfg.c** 里有一张配置表，注册了每个 SID 的入口函数、需要的会话状态、安全访问等级。新增一个服务只需要在这里加一行配置，然后写一个处理函数就行了——**框架是高度可扩展的**。

### 要点提炼

| 层级 | 目录 | 核心职责 |
|------|------|---------|
| 业务层 | UDSLogic/ | SID 处理函数，每个文件一个服务 |
| 协议层 | UDSBase/ | ISO-TP 组包/拆包 + 服务分发 + 会话管理 |
| 硬件层 | Core/Src/ | CAN/USART/Flash/IWDG/AES 驱动封装 |
| 缓冲层 | RingBuf/ | CAN 消息环形队列，中断→主循环传参 |

## 五、通信协议栈 (CAN → ISO-TP → UDS)

⏱ 8 min

### 讲解词

> 通信协议栈分三层，我们一层一层展开：

### 5.1 物理层 — CAN 总线

> 最底层是 **CAN 2.0B**，经典 CAN，500kbps，标准帧 11 位 ID。
>
> 我们定义了两组 ID：
> - **Tester → ECU**: `0x123`（物理请求）
> - **ECU → Tester**: `0x122`（物理响应）
> - **功能寻址**: `0x7DF`（保留，当前未用）
>
> 为什么用 0x123 / 0x122 这么大？因为 CAN 标准帧 ID 范围是 0~0x7FF，小 ID 优先级更高。但我们这是点对点诊断通信，不涉及实时抢占，所以用大 ID 完全没问题，反而在调试时更容易辨认。
>
> 每帧数据长度固定 **8 字节**，不够的填 `0xAA` 作为填充。

### 5.2 传输层 — ISO 15765-2 (ISO-TP)

> 这一层解决一个核心问题：**CAN 一帧只能发 8 字节，但 UDS 报文可能长达几十上百字节**，怎么办？
>
> ISO-TP 定义了四种帧类型来解决这个问题：

| 帧类型 | PCI 首字节 | 作用 |
|--------|-----------|------|
| **单帧 (SF)** | `0x00~0x07` | ≤7 字节的数据，一帧搞定 |
| **首帧 (FF)** | `0x10~0x1F` | 通知接收方：后面要跟 N 字节的数据 |
| **连续帧 (CF)** | `0x20~0x2F` | 后续数据，按顺序发 |
| **流控帧 (FC)** | `0x30~0x3F` | 接收方告诉发送方：继续发 / 等一等 / 满了 |

> 举个例子，如果我们要发一个 20 字节的 UDS 请求：
>
> 1. 发送方先发一个 **首帧**：PCI 中包含总长度 20
> 2. 接收方回一个 **流控帧**：告诉发送方 "可以发，一次最多发 2 帧，帧间隔 0ms"
> 3. 发送方发 **连续帧** #1、#2（各 7 字节数据）
> 4. 如果还有数据，可能需要再次等待流控帧——这就是 Block Size 机制
>
> **可以理解为 ISO-TP 是一个精简版的 TCP**：有拆包、组包、流量控制、超时重传。

### 5.3 应用层 — UDS (ISO 14229-1)

> 再往上一层就是 UDS——统一诊断服务。它定义了我们能做什么操作，数据格式是什么样的。
>
> **基本消息格式：**
> - **请求**: `SID + SubFunction / 参数`
> - **正响应**: `(SID+0x40) + 数据`
> - **负响应**: `0x7F + SID + NRC`（错误码）
>
> 举个例子，请求切换到编程会话：
> - 发 → `10 02`（SID 0x10 + 子功能 0x02 = 编程会话）
> - 收 → `50 02`（正响应：0x10+0x40 = 0x50）
>
> 如果当前条件不满足，比如没解锁安全访问就尝试擦 Flash，ECU 就会回：
> - `7F 31 33`（服务 0x31 被拒绝，原因 0x33 = Security Access Denied）
>
> **会话管理**是 UDS 的一个基础概念。我们支持三种会话：
> - **默认会话 (0x01)** — 上电后的初始状态，只能执行基础服务
> - **扩展会话 (0x03)** — 允许诊断类操作
> - **编程会话 (0x02)** — 允许固件刷写类操作
>
> 如果在当前会话下 5 秒内没有收到诊断请求（没有发 0x3E 保活），ECU 会自动退回默认会话。这叫 **S3Server 超时**，是一个安全机制，防止诊断会话意外挂起。

### 5.4 安全访问 (SID 27)

> 固件刷写涉及安全敏感操作，不能谁连上 CAN 总线都能刷。所以我们实现了 **SID 27 - SecurityAccess**。
>
> 流程是标准的 **挑战-响应（Challenge-Response）**：
>
> 1. Tester 发 `27 01` 请求种子
> 2. ECU 返回一个随机种子 `67 01 + [4字节随机数]`
> 3. Tester 用 **AES-128 CMAC** 算法，用预先共享的密钥对种子计算消息认证码
> 4. Tester 发 `27 02 + [CMAC结果]`
> 5. ECU 用同样的密钥和算法计算一遍，对比——匹配就通过
>
> 为什么用 CMAC 而不是简单的 CRC 或累加和？因为 CMAC 是 **密钥相关的**——没有密钥的人即使知道算法也算不出正确结果，相当于一把电子锁。

## 六、Flash 内存布局

⏱ 3 min

### 讲解词

> 下面是一张从 **0x08000000** 开始的 Flash 地址空间图：

```
0x08000000 ┌──────────────────────┐
           │  FBL 核心代码 (32KB)  │  ← 中断向量表 + 引导代码
0x08007FFC │  FBL 版本号 (4B)     │  ← ASCII 字符串
0x08008000 ┌──────────────────────┤
           │  隔离预留区 (8KB)     │  ← 防止 FBL/APP 越界干扰
0x08009FFF │──────────────────────│
0x0800A000 │  APP 有效标志 (4B)    │  ← 0x5A5A5A5A
0x0800BFFF │──────────────────────│
0x0800C000 │  APP 核心代码 (80KB)  │  ← 应用程序主体
0x0801FFFC │  APP 版本号 (4B)     │  ← ASCII 字符串
           └──────────────────────┘
```

> 几个设计要点：
>
> **为什么 FBL 只占 32KB？** Bootloader 的逻辑相对固定，32KB 完全够用。留出更多空间给 APP。
>
> **中间 8KB 是隔离区。** 这片区域谁都不属于，也不存放有效数据。它的作用是：即使 FBL 或 APP 有 bug、指针越界写了不该写的地方，隔离区提供了一重缓冲，不会直接破坏对方的代码。
>
> **APP 有效标志** 单独占了一个 4 字节地址（0x0800A000），不在 APP 代码区内部。这样做的原因是：我们要判断 APP 是否有效，不需要解析 APP 的整个镜像，只需要看这一个标志位就行。
>
> **版本号** 存放在固定地址的 4 字节中，格式是 ASCII，比如 "V1.0"。这样可以通过 UDS 的 ReadDataByIdentifier 服务直接读取，不需要算偏移。

## 七、UDS 服务详解与刷写流程

⏱ 8 min

### 讲解词

> 我们实现了 **16 个 UDS 服务**，按功能大致可以分为五类：

### 服务分类

**① 会话与连接管理**
- 0x10 — DiagnosticSessionControl：切换会话
- 0x3E — TesterPresent：保活，防止 S3Server 超时

**② 诊断与故障管理**
- 0x14 — ClearDiagnosticInformation：清除故障码
- 0x19 — ReadDTCInformation：读取故障码信息
- 0x85 — ControlDTCSetting：启用/禁用故障码记录

**③ 数据访问**
- 0x22 — ReadDataByIdentifier：按 DID 读数据
- 0x2E — WriteDataByIdentifier：按 DID 写数据

**④ 安全与维护**
- 0x11 — ECUReset：软件复位 / 硬件复位
- 0x27 — SecurityAccess：种子+密钥 安全解锁
- 0x28 — CommunicationControl：控制通信启用/禁用

**⑤ 固件刷写（核心流程）**
- 0x31 — RoutineControl：擦 Flash / 校验签名 / 查完成
- 0x34 — RequestDownload：请求下载，ECU 分配空间
- 0x36 — TransferData：传数据，支持分块连续传输
- 0x37 — RequestTransferExit：结束传输

> 其中 **0x34 / 0x36 / 0x37** 三个服务构成了固件刷写的主流程。

### 完整刷写流程演示

> 下面是一个完整的刷写时序，我一步步解释：

```
Tester                                    ECU
  │                                        │
  │① 进入扩展会话                          │
  ├─ 0x10 03 ────────────────────────────►│
  │◄─ 0x50 03 ────────────────────────────┤
  │                                        │
  │② 安全解锁 (种子+密钥)                  │
  ├─ 0x27 01 ────────────────────────────►│
  │◄─ 0x67 01 + Seed ─────────────────────┤
  ├─ 0x27 02 + CMAC ─────────────────────►│
  │◄─ 0x67 02 ────────────────────────────┤
  │                                        │
  │③ 切换编程会话                          │
  ├─ 0x10 02 ────────────────────────────►│
  │◄─ 0x50 02 ────────────────────────────┤
  │                                        │
  │④ 擦除 Flash                           │
  ├─ 0x31 01 FF00 ───────────────────────►│
  │◄─ 0x71 01 FF00 ───────────────────────┤
  │                                        │
  │⑤ 请求下载 (协商大小)                   │
  ├─ 0x34 + 参数 ────────────────────────►│
  │◄─ 0x74 + 块大小 ──────────────────────┤
  │                                        │
  │⑥ 循环传输数据块                        │
  ├─ 0x36 + SN + Data ───────────────────►│  ┐
  │◄─ 0x76 + SN ──────────────────────────┤  │ 重复多次
  │            ...                         │  ┘
  │                                        │
  │⑦ 结束传输                             │
  ├─ 0x37 ───────────────────────────────►│
  │◄─ 0x77 ───────────────────────────────┤
  │                                        │
  │⑧ 校验编程完成                          │
  ├─ 0x31 01 0205 ───────────────────────►│
  │◄─ 0x71 01 0205 ───────────────────────┤
  │                                        │
  │⑨ 硬件复位 → 跳转 APP                  │
  ├─ 0x11 01 ────────────────────────────►│
  │                                        │
```

> 这里有几个关键细节：
>
> **为什么先扩展会话再编程会话？** 因为安全访问服务（27）只在默认和扩展会话下可用，编程会话要先解锁才能进入。
>
> **RequestDownload（34）的作用是什么？** 它实际上是一次"协商"。Tester 告诉 ECU "我想下载这么多字节"，ECU 根据自身 Flash 剩余空间回复"可以，你每个块最多发 XX 字节"。
>
> **TransferData（36）** 每帧携带数据和一个块序号。ECU 通过序号可以检测丢帧和乱序。如果序号不连续，说明有丢帧，ECU 应该回复错误。
>
> **Routine 0x0205（查完成）** 在传输结束后调用，ECU 会对整个 APP 区域计算 CRC16-CCITT，和固件包里的预期值做对比，确认数据没有损坏。

### 要点提炼

```
完整刷写路径:
10 03 → 27 01/02 → 10 02 → 31 FF00(擦除)
→ 34(请求下载) → 36×N(传数据) → 37(退出)
→ 31 0205(校验) → 11 01(复位)
```

## 十、项目总结与展望

⏱ 1 min

### 讲解词

> 回顾一下，这个项目从底到顶实现了 **一套完整的、基于 CAN 总线的 UDS Bootloader**：
>
> - **硬件** 选择了成本友好、生态成熟的 STM32F103
> - **通信** 基于 CAN 2.0，ISO-TP 做多帧传输，UDS 做应用层协议
> - **安全** 用 AES-CMAC 做挑战-响应认证
> - **可靠性** 靠 IWDG 独立看门狗兜底
> - **工具链** 同时支持 CMake/Ninja、GNU Make、Keil MDK 三种构建方式
> - **测试** 配套了完整的 Python PCAN 工具链，支持单服务调试和一键刷写

### 可能的演进方向

> 几个可以继续深化的方向：
>
> 1. **支持 CAN FD** — 如果换用支持 CAN FD 的芯片（如 STM32G4、H7），每帧数据可以从 8 字节提升到 64 字节，刷写速度翻倍
> 2. **加密固件** — 传输过程中对固件包做 AES 加密，防止在 CAN 总线上被嗅探窃取
> 3. **压缩传输** — 固件先压缩再传输，ECU 收到后解压写入，减少传输时间
> 4. **功能寻址广播** — 目前 0x7DF 功能地址预留但未实现，后续可以支持同时刷新多个 ECU

## 附录 A: NRC 负响应码速查

| NRC | 含义 | 常见原因 |
|-----|------|---------|
| 0x11 | 服务不支持 | ECU 没有实现该 SID |
| 0x12 | 子功能不支持 | SID 存在但子功能无效 |
| 0x13 | 报文长度错误 | 参数比期望的短或长 |
| 0x22 | 条件不满足 | 当前状态不允许该操作 |
| 0x24 | 请求顺序错误 | 比如没 RequestDownload 就 TransferData |
| 0x31 | 参数超出范围 | DID 或 RID 不存在 |
| 0x33 | 安全访问被拒 | 当前会话未解锁 |
| 0x35 | 密钥无效 | CMAC 认证失败 |
| 0x36 | 尝试次数超限 | 安全解锁重试太多次 |
| 0x37 | 延时未到 | 连续安全请求间隔太短 |
| 0x78 | 请求处理中 | ECU 需要更多时间，Tester 应等待 |
| 0x7F | 当前会话不支持 | 切换回默认会话或更高权限会话 |
